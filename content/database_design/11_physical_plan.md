## 11장. 논리적 설계를 물리적 설계로 전환하기 핵심 정리

### 1. 물리적 설계 개요 및 논리적 설계와의 차이

* **물리적 DB 설계란?** 논리적 설계 산출물(ERD)의 요소를 관계형 데이터베이스 요소로 전환하고, 성능과 DBMS 특성을 고려해 반정규화·인덱스·뷰 등을 설계하는 단계입니다.


* **주요 설계 활동**
* 엔티티, 관계, 속성을 테이블, 컬럼, 키 등으로 변환합니다.


* 성능을 고려해 반정규화 과정을 시행합니다.


* 인덱스와 뷰를 설계합니다.




* **사전 조사 및 분석 항목**
* 사내 명명 규칙 및 데이터 표준화 요소 파악·반영


* 하드웨어 자원 파악(CPU, MEMORY, DISK, I/O Controller, Network)


* 운영 체제, DBMS 버전 및 DBMS 파라미터 확인





| 구분 | 논리적 DB 설계 (데이터 모델링) | 물리적 DB 설계 |
| --- | --- | --- |
| **DBMS 의존성** | DBMS 종류·제품과 무관하게 진행| 특정 DBMS를 전제로 특성 고려하여 진행|
| **주요 구성요소** | 엔티티, 속성, 주식별자, 외래식별자| 테이블, 컬럼, 기본키(PK), 외래키(FK), 뷰, 인덱스|

---

### 2. 테이블, 컬럼, 키, 관계로의 전환

* **물리 데이터 모델링 절차**
1. ENTITY별 테이블 단위 결정


2. UID를 기본키(PK)로 전환(속성 식별자 `#`, 릴레이션쉽 식별자 `uid bar`)


3. 일반 속성(non-key attribute)의 컬럼 전환


4. 일반 RELATIONSHIP의 컬럼 전환


5. 배타적 관계 전환형태 결정


6. 각종 제약조건, 파라미터 결정




* **요소별 전환 규칙**
* **엔티티 → 테이블:** 엔티티를 테이블로 변환하며, 한글 엔티티명을 영문 테이블명으로 바꿉니다(예: `도서` → `book`).


* **속성 → 컬럼:** 용어사전 등을 활용해 한글 속성명을 영문 컬럼명으로 바꾸고 데이터 타입을 지정합니다(예: `제목` → `title varchar(100)`).


* **식별자 → 키:** 주식별자는 기본키(PK), 외래식별자는 외래키(FK)로 전환합니다.


* **관계:** 논리적 설계의 엔티티 간 관계는 물리적 설계에서도 그대로 유지합니다.





---

### 3. 반정규화 (De-normalization)

* **정의:** 정규화의 반대 개념으로, 어느 정도의 중복을 감수하고 데이터베이스의 성능(특히 검색 속도)을 높이기 위해 ERD를 정규화 이전 상태로 변경하는 과정입니다.


* **특징 및 유의점**
* 정규화가 엔티티를 분리한다면, 반정규화는 엔티티를 통합하는 방향으로 진행됩니다.


* 데이터 무결성 문제가 발생할 수 있으므로 반드시 대비책이 필요합니다.


* 반정규화 없이 성능을 향상시킬 수 있는 대안이 있다면 이를 우선 고려하는 것이 바람직합니다.





---

### 4. 뷰(View)와 인덱스(Index) 설계

* **뷰(View) 설계 (모델링 도구 기준)**
1. `[Home]` → `[View]` 선택 후 ERD 빈 곳을 클릭해 뷰 템플릿을 생성합니다.


2. 뷰 이름을 입력합니다(예: `view_golden_member`).


3. 우클릭 후 `[View Properties...]`에서 `[From]` → `[Select]` → `[Clauses]` 순서로 뷰 생성 조건(예: `Where: golden_member_yn = 'Y'`)을 설정합니다.




* **인덱스(Index) 설계**
* 테이블 검색 속도를 높이는 수단으로, 책의 색인과 유사한 역할을 합니다.


* 모델링 도구에서 테이블 편집기의 `Indexes` 탭이나 Index Editor를 통해 Unique/Non-Unique 인덱스를 생성하고 대상 컬럼과 정렬 순서(`Ascending` / `Descending` 등)를 지정할 수 있습니다.





---

### 5. 테이블 기술서와 도서관 관리 설계 예시

* **테이블 기술서:** 개별 테이블의 상세 정보를 문서화한 자료로, 시스템명, 테이블 설명, 컬럼별 데이터 타입, NN(Not Null), KY(PK/FK/PFK), Default, 비고(상태 코드, 인덱스 지정, 참조 무결성 등)를 담아 개발 및 유지보수에 활용합니다.


* **도서관 관리 예시:** 논리적 ERD(`회원`, `대출`, `대출내용`, `도서`, `작품`, `업체`, `세금계산서`, `독서클럽`, `도서대출통계`, `듀이분류표`, `환경변수` 등)가 물리적 ERD(`member`, `rent`, `book`, `product`, `company`, `tax_bill`, `tax_invoice`, `book_club`, `rent_statistics`, `dewei_table`, `env_variable`, `view_golden_member` 등)로 전환된 구조를 보여줍니다.

## 시험에 자주 나오는 핵심 포인트

### 1. 논리적 DB 설계 vs 물리적 DB 설계 비교

* **논리적 DB 설계:** DBMS 종류나 제품과 무관하게 진행하며, 엔티티·속성·주식별자·외래식별자 중심입니다.


* **물리적 DB 설계:** 특정 DBMS를 전제로 특성을 고려해 진행하며, 테이블·컬럼·기본키(PK)·외래키(FK)·뷰·인덱스 등으로 전환합니다.



### 2. 요소 전환 대응 관계

* **엔티티 → 테이블**


* **속성 → 컬럼**


* **주식별자 → 기본키(PK)**


* **외래식별자 → 외래키(FK)**


* **관계·카디널리티·참여도:** 논리적 설계의 관계 구조가 물리적 설계에서도 유지됩니다.



### 3. 반정규화 (수직분할·수평분할·속성 중복)

* **수직분할:** 부서별 등 필요 정보(컬럼)가 다를 때 엔티티를 컬럼 단위로 분할합니다.


* **수평분할:** 튜플의 검색 빈도 차이(예: 자주 검색되는 상위 20%와 나머지 80%)를 이용해 데이터 크기를 줄이고 검색 성능을 높입니다.


* **속성 중복:** 조인해서 가져오는 속성이 적을 때는 엔티티 통합보다 속성을 중복 저장하는 편이 합리적이며, 데이터 무결성 이슈를 고려해야 합니다.



### 4. 인덱스 성능 조건 및 검토 기준 (출제 빈도 높음)

* 인덱스가 많으면 재정렬 비용으로 DBMS 성능이 저하되므로 **꼭 필요한 컬럼에만 지정**해야 합니다.


* **WHERE 절 비교 대상 컬럼** 또는 **JOIN에 사용되는 컬럼**이어야 효과적입니다.


* 튜플 수가 적으면(예: 200~300개) 효과가 크지 않습니다.


* 검색 결과가 **전체 튜플의 10~15% 미만**일 때 인덱스의 효과가 있습니다.



### 5. 테이블 기술서 약어 의미

* **NN:** Not Null(선택 시 Null을 허용하지 않음)


* **KY:** Key(기본키 `PK`, 외래키 `FK`, 기본키이면서 외래키인 경우 `PFK`)
