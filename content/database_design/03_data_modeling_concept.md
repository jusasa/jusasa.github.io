# 데이터 모델링 주요 개념

## 1. 개요

### 1.1 데이터 모델링의 개념 및 목적
- **개념**: 정보 시스템을 구축하는 데 필요한 정보(데이터)를 약속된 표기법에 의해 표현하는 과정 (현실 세계 관찰/분석 $\rightarrow$ 개념적 모델(ERD) $\rightarrow$ 논리/물리 데이터베이스 구축).
- **목적**:
  - 시스템 구축 대상이 되는 업무 내용을 정확하게 분석.
  - 분석된 모델을 바탕으로 실제 데이터베이스를 생성하여 개발 및 관리에 활용.
- **주요 특징**:
  - 전체 데이터베이스 설계에서 가장 핵심적인 단계 (`논리적 데이터베이스 설계` $\cong$ `데이터 모델링`).
  - 효율적인 모델링을 위해 모델링 CASE 도구를 활용하기도 함.
  - 데이터 모델링의 최종 산출물(Output)은 **ERD (Entity Relationship Diagram)**.

### 1.2 데이터 모델링의 3가지 핵심 요소
1. **엔티티 (Entity)**: 업무의 관심 대상이 되는 사물이나 객체
2. **속성 (Attribute)**: 엔티티가 가지는 세부 정보 항목
3. **관계 (Relationship)**: 엔티티 간의 의미 있는 상호 연관성

### 1.3 데이터베이스 용어 vs 모델링 용어
| 데이터베이스 용어 (물리적 설계) | 모델링 용어 (데이터 모델링) |
| :--- | :--- |
| **테이블 (Table)** | **엔티티 (Entity)** |
| **컬럼 (Column), 열** | **속성 (Attribute)** |
| **튜플 (Tuple), 행 (Row)** | **인스턴스 (Instance)** |
| **기본키 (Primary Key, PK)** | **주식별자 (Primary Identifier)** |
| **외래키 (Foreign Key, FK)** | **외래 식별자 (Foreign Identifier)** |

## 2. 엔티티 (Entity)

### 2.1 정의 및 표현
- **정의**: 업무의 관심 대상이 되는 정보를 갖고 있거나 그에 대한 정보를 알아야 하는 유·무형의 사물이나 객체.
- **예시**:
  - 유형: 고객, 사원정보, 부서, 제품, 학생, 교수 등
  - 무형: 생산계획, 부서조직, 공정 등
  - 문서/전표: 주문서, 성적표, 입고전표, 금전출납부 등
- **엔티티와 인스턴스**:
  - `엔티티`: 집합적인 개념 (예: 회원)
  - `인스턴스`: 엔티티 집합에 속한 개별 개체 (예: 홍길동, 김철수, 강만길)

### 2.2 엔티티의 분류
- **유형 엔티티**: 물리적 형태가 있고 쉽게 식별 가능한 엔티티 (예: 고객, 사원, 상품, 거래처, 학생)
- **무형 엔티티**: 물리적 형태 없이 개념적으로 존재하는 엔티티 (예: 생산계획, 부서조직, 색상별선호도)
- **문서 엔티티**: 업무 절차상 사용되는 문서, 장부, 전표에 대한 엔티티 (예: 거래명세서, 입출금전표, 주문서, 금전출납부)
- **이력 엔티티**: 업무상 반복적으로 발생하는 행위나 사건을 일자/시간별로 관리하기 위한 엔티티 (예: 입고이력, 출고이력)
- **코드 엔티티**: 공통 코드나 각종 분류 코드를 체계적으로 관리하기 위한 엔티티 (예: 국가코드, 색상코드, 직급분류코드, 상태코드)

### 2.3 엔티티의 특징
1. **업무 필요성**: 구축 대상이 되는 업무에서 반드시 필요하고 관리하고자 하는 정보여야 함 (예: 병원 시스템에서의 '환자'는 필수 엔티티이나, 일반 회사 시스템에서는 불필요).
2. **인스턴스 복수성**: 일반적으로 2개 이상의 인스턴스가 존재해야 엔티티로서 의미가 있음.
3. **속성 보유**: 반드시 1개 이상의 속성을 가져야 함 (속성을 도출할 수 없다면 엔티티가 아닌 다른 엔티티의 속성일 가능성이 높음).

### 2.4 엔티티 명명 규칙
- 현업 업무에서 실제로 사용하는 용어를 사용
- 가급적 약어 사용을 지양
- 단수 명사 사용
- 모든 엔티티명은 시스템 내에서 유일해야 함
- 엔티티 생성 목적과 의미가 직관적으로 드러나도록 명명

## 3. 속성 (Attribute)

### 3.1 정의 및 특징
- **정의**: 엔티티에서 관리하고자 하는 더 이상 분리되지 않는 최소 단위의 데이터.
- **엔티티와의 관계**: 엔티티는 1개 이상의 속성으로 구성되며, "속성들의 집합"으로 정의될 수 있음.
- **테이블 대응**: 엔티티의 각 속성은 물리적 데이터베이스 테이블의 **컬럼(Column)**에 대응됨.
- **속성 선별**: 현실 세계의 무수한 정보 중 해당 업무 시스템에서 관심 있는 항목만 선별하여 속성으로 정의함.

### 3.2 속성의 분류
- **기본 속성 (Basic Attribute)**: 업무 분석을 통해 현실 세계로부터 직접 도출된 본래의 속성 (예: 제품이름, 제조년월, 원가)
- **설계 속성 (Designed Attribute)**: 현실 세계에는 없으나 시스템 설계 편의나 규칙을 위해 새로 정의한 속성 (예: 일련번호, 국가코드, 색상코드)
- **유도 속성 (Derived Attribute)**: 다른 속성들의 값으로부터 계산이나 변형에 의해 산출되는 속성 (예: 금액 = 수량 $\times$ 단가, 평균 = 합계 / 인원수)

### 3.3 속성 명명 규칙
- 속성의 의미가 분명하게 드러나도록 명명 (해당 업무 용어 사용)
- 서술식 명칭 지양 (수식어나 소유격 표현 자제)
- 가급적 약어 사용 지양
- 엔티티 내에서 유일하게 식별 가능하도록 지정
- 용어 혼란을 방지하기 위해 사전에 **데이터 사전(Data Dictionary)**을 정의하여 표준화

## 4. 관계 (Relationship)

### 4.1 정의
- 두 개 또는 그 이상의 엔티티 간의 의미 있는 연관성.
- 엔티티와 엔티티가 존재의 형태나 행위로 상호 영향을 주고받는 형태.
- **공유 속성**: 두 엔티티가 관계를 맺고 있다는 것은 상호 간에 연결 고리가 되는 **공유 속성**이 존재함을 의미 (단, 두 엔티티 간 공유하는 속성명이 반드시 일치할 필요는 없음).

### 4.2 관계의 명명
- 관계를 맺는 양방향 엔티티 관점에 따라 각각 이름을 부여할 수 있음.
  - 예: `학생` $\rightarrow$ `수강과목` : "수강한다"
  - 예: `수강과목` $\rightarrow$ `학생` : "수강된다"

### 4.3 관계의 카디널리티 (Cardinality)
두 엔티티 간 관계에서 각 인스턴스가 참여할 수 있는 수량적 대응 관계.
- **1 : 1 (일대일)**: 양쪽 엔티티의 인스턴스가 서로 1개씩 대응됨. 필요에 따라 두 엔티티를 하나로 통합 가능 (예: 학생 - 신체정보).
- **1 : N (일대다)**: 한쪽 엔티티의 인스턴스가 상대 엔티티의 여러 인스턴스와 대응됨. 데이터 모델링에서 가장 흔한 관계 (예: 학생 - 학생의취미, 부서 - 사원).
- **M : N (다대다)**: 양쪽 모두 여러 인스턴스와 대응됨. 관계형 데이터베이스로 직접 구현할 수 없으므로, **교차/연결 엔티티(Intersection Entity)**를 추가하여 **1:N, N:1 관계로 해소**해야 함 (예: 제품 - 제조업체).

### 4.4 관계의 참여도 (Optionality)
두 엔티티의 인스턴스가 관계에 반드시 참여해야 하는지 여부.
- **필수 참여 (`|`)**: 해당 인스턴스가 존재하기 위해 반드시 상대 엔티티의 인스턴스와 연관되어야 함.
- **선택 참여 (`O`)**: 상대 인스턴스와 연관되지 않고도 단독으로 존재할 수 있음.
- *예시*:
  - 사원은 반드시 하나의 부서에 소속되어야 함 $\rightarrow$ **사원 관점: 필수**
  - 신설 부서의 경우 소속 사원이 아직 없을 수도 있음 $\rightarrow$ **부서 관점: 선택**

### 4.5 부모 엔티티와 자식 엔티티
- **구분 기준**: 어느 쪽의 데이터가 먼저 생성되는가에 따라 결정.
  - **부모 엔티티**: 정보가 먼저 생성되는 쪽 (예: 학생, 부서)
  - **자식 엔티티**: 부모의 정보를 가져다 쓰는 쪽 (예: 학생의취미, 사원)
- **일반적 특성**: 부모와 자식 간에는 카디널리티가 **1 : N**이며, 부모 쪽이 **필수**, 자식 쪽이 **선택**인 경우가 일반적임.

## 5. 주식별자와 외래 식별자

### 5.1 식별자(Identifier)와 키(Key)의 비교
| 모델링 단계 (데이터 모델링) | 물리적 DB 설계 단계 | 설명 |
| :--- | :--- | :--- |
| **주식별자 (Primary Identifier)** | 기본키 (Primary Key) | 엔티티 내에서 각 인스턴스를 유일하게 구별하는 기준 |
| **외래식별자 (Foreign Identifier)** | 외래키 (Foreign Key) | 다른 엔티티와의 연관 관계를 맺어주는 연결 고리 |
| **보조식별자 (Alternate Identifier)** | 대체키 (Alternate Key) | 주식별자를 대신하여 인스턴스를 유일하게 식별할 수 있는 속성 |

### 5.2 주식별자 (Primary Identifier)
- 엔티티 내에서 인스턴스를 고유하게 식별할 수 있는 최소한의 속성.
- ERD 표기: 일반적으로 속성명 앞에 `◆` 기호를 붙이거나 `(PK)`로 표시.
- **Null 허용 여부**: 관계형 데이터베이스에서 주식별자는 **절대로 Null 값을 가질 수 없음 (Not Null)**.

### 5.3 외래 식별자 (Foreign Identifier)
- 엔티티 간의 관계를 맺어주는 연결 고리 역할을 하는 속성.
- ERD 표기: 속성명 뒤에 `(FK)`로 표시.
- **부모-자식 연결**: 부모 엔티티의 **주식별자(PK)**가 자식 엔티티의 **외래식별자(FK)**로 상속되어 연결됨.
- **Null 허용 여부**: 관계형 데이터베이스에서 외래식별자는 업무 규칙에 따라 **Null 값을 가질 수 있음**.

## 6. ERD (Entity Relationship Diagram) 표기법

### 6.1 발전 과정
- **초기 ERD (Chen 표기법 등)**: 엔티티(직사각형), 관계(다이아몬드), 속성(타원)으로 각각 분리하여 복잡하게 표현함.
- **현대적 ERD (Information Engineering 표기법 등)**: 
  - 엔티티를 사각형 블록으로 표현.
  - 상단에는 **주식별자(PK)**, 하단에는 **일반 속성 및 외래식별자(FK)**를 일목요연하게 기재.
  - 엔티티 간 선에 까마귀발(Crow's foot, 다중), 실선/바(Bar, 단일/필수), 원(Circle, 선택)을 조합하여 카디널리티와 참여도를 직관적으로 표시.

### 6.2 데이터 모델링 종합 흐름 요약
1. **현실 세계 분석**: 비즈니스 업무 규칙 및 요구사항 도출 (예: 도서 대출 요청 및 대출기록부 작성).
2. **개념적/논리적 모델링 (ERD 작성)**:
   - 주요 엔티티 식별 (`학생`, `도서`, `대출기록부`)
   - 식별자 정의 (주식별자 및 외래식별자 도출)
   - 카디널리티 및 참여도 관계 설정 (`학생` 1 : N `대출기록부` N : 1 `도서`)
3. **물리적 데이터베이스 구현**:
   - 엔티티를 실제 DB 테이블로 변환
   - 속성을 컬럼으로, 인스턴스를 튜플(레코드)로 저장하여 데이터베이스 구축.
