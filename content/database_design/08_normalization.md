# 8. 정규화 (Normalization)

## 8.1 개요

정규화(normalization)란?
- ERD 내에서 중복 요소를 찾아 제거해 나가는 과정
- 중복된 데이터는 많은 문제를 일으킨다
- **3차 정규화 정도만 알면 설계하는데 무리가 없다**
- 몇 가지 원칙만 지키면 정규화가 필요 없는 ERD를 설계할 수 있다

정규화의 의미
- 관계형 데이터베이스의 개념이지만, 그 원칙은 데이터 모델링에도 적용됨
- 정규화 단계별 규칙을 사용하여 ATTRIBUTE의 위치를 적절히 하는 것
- 정규화 작업이 완료된 E-R Model은 바로 정규화된 관계형 데이터베이스 설계로 옮겨진다
- **제3정규형은 데이터 중복을 제거하기 위한 데이터베이스 설계의 일반적인 목표**
- 그 이상의 정규형은 별로 폭넓게 사용되지 않는다

| 정규형 | 규칙 |
| --- | --- |
| 제1정규형 | 모든 ATTRIBUTE는 반드시 하나의 값을 가져야 한다 (반복 형태가 있어서는 안 됨) |
| 제2정규형 | 모든 ATTRIBUTE는 반드시 주식별자에 종속되어야 한다 |
| 제3정규형 | 주식별자가 아닌 속성 간에는 서로 함수적 종속될 수 없다 (ATTRIBUTE 간 종속성 배제) |

## 8.2 정규화 과정

### 제1 정규화 (1st NF)

정의
- 엔티티에서 하나의 속성이 복수개의 값을 갖도록 설계되어 있을 때, 하나의 속성이 단일 값(atomic value)을 갖도록 설계를 변경하는 과정

핵심
- **모든 ATTRIBUTE는 반드시 하나의 값을 가져야 한다 (반복 형태가 있어서는 안 됨)**
- 예) 취미가 등산인 사원을 찾으려면? → 취미가 여러 값이면 검색이 어려움
- 동일 속성이 반복되는 경우도 제1 정규화가 필요

새 엔티티 추가
- 어떤 ATTRIBUTE가 다수의 값을 가지고 있다면 **M:1 관계의 새로운 ENTITY를 추가**한다
- 한 고객이 여러 계약일을 가져야 한다면 → 계약 엔티티를 분리
- **속성검증 2단계(유일값 검증)와 동일**
- 즉, 제1 정규화는 속성검증 단계에서 실시하라는 의미
- 나중에 이력관리 결정에 의해 제1 정규형이 추가될 수 있음
- 유사한 속성을 묶어 개념을 상향조정하면 제1 정규형에 저촉됨
- 속성검증 4단계(관리수준 상세화)에서 나타날 수도 있음

예제 (판매 엔티티)
- 이전: 판매(판매일자, 판매부서, 판매번호, 부서명, 판매사원번호, 사원명, 고객번호, 고객명, 고객주소, 제품번호1, 제품명1, 단가1, 수량1, 금액1, 제품번호2 …)
- 이후: 판매 엔티티 + **판매내역** 엔티티(판매일자(FK), 판매부서(FK), 판매번호(FK), 일련번호, 제품번호, 제품명, 단가, 수량, 금액)로 분리

### 제2 정규화 (2nd NF)

정의
- **주식별자가 아닌 속성들 중에서, 주식별자 전체가 아닌 일부 속성에 종속된 속성을 찾아 제거하는 과정** (부분 함수 종속 제거)

예
- 부서명은 판매부서 번호에 의해 결정된다 → 부서명이 판매부서에 종속
- 종속 관계에 의한 데이터 중복 및 불일치 사례

| 판매일자 | 판매부서 | 판매번호 | 부서명 | 사원번호 | 사원명 |
| --- | --- | --- | --- | --- | --- |
| 05.11.2 | DH01 | 01 | 영업1부 | 1001 | 홍길동 |
| 05.11.2 | DH01 | 02 | 영업1부 | 1009 | 김철수 |
| 05.11.2 | DH01 | 03 | **생산부** | 1001 | 홍길동 |
| 05.11.3 | DH01 | 01 | 영업1부 | 1010 | 조창인 |

→ 같은 DH01 부서인데 부서명이 "영업1부"와 "생산부"로 **불일치** 발생

정규화 결과
- 판매 엔티티에서 부서 관련 속성을 떼어내어 **부서** 엔티티(부서번호, 부서명)로 분리
- 학생 예: 학생(학번, 성명) / 교육과목(과목코드, 과목명, 개설기간)

### 제3 정규화 (3rd NF)

정의
- **주식별자가 아닌 속성들 중에서 종속관계에 있는 속성을 찾아 제거하는 과정** (이행 함수 종속 제거)

정규화 결과 (판매 예)
- 판매 엔티티에서 사원/고객/제품 관련 속성을 각각 분리
- 판매(판매일자, 판매부서(FK), 판매번호, 판매사원번호(FK), 고객번호(FK))
- **사원**(사원번호, 사원명), **고객**(고객번호, 고객명, 고객주소), **제품**(제품번호, 제품명, 단가)
- 판매내역(판매일자(FK), 판매부서(FK), 판매번호(FK), 일련번호, 제품번호(FK), 수량, 금액)
- 평가 예: 평가(평가코드, 평가내역)

정규화 연습
- 수강등록(학점, 교수번호, 학점설명, 강좌명) 형태의 E-R 모델을 제3 정규형에 맞도록 다시 작성
- → 수강등록, 학생(학번, 성명), 강좌(강좌번호, 강좌명), 학점(학점코드, 학점실명), 교수(교수번호, 교수명), 학과(학과코드, 학과명)로 분리하고 관계를 맺음

## 8.3 정규화에서 엔티티의 분리

- 정규화 과정은 결국 **중복을 제거하기 위해 엔티티를 여러 개로 분리하는 과정**이다
- 정규화를 거치게 되면 자연히 엔티티의 수가 늘어나게 된다
- **엔티티를 그냥 분리하면 두 엔티티 사이에 관계가 없어져 버리므로, 관계를 맺으면서 분리해야 한다**
- 이 방법은 제2 정규화와 제3 정규화 과정에 공통적으로 적용될 수 있다

분리 절차 (판매 예)
1. 종속관계에 있는 정보(예: 판매부서에 종속된 부서명)를 별도의 엔티티에 저장
2. 판매 엔티티에서는 종속된 속성을 제거하고 해당 키를 **외래키(FK)** 로 지정
3. 부서 엔티티가 부모, 판매 엔티티가 자식이 되므로 그에 맞게 관계 설정

## 8.4 정규화가 필요 없는 설계 기법

개요
- 정규화를 잘 할 수 있게 되는 것도 중요하지만, **정규화가 필요 없도록 모델링을 할 수 있다면 그것이 더 바람직**하다
- 실제로 정규화를 잘 이해하고 있는 설계자는 정규화를 할 필요가 없도록 모델링을 한다

**원칙1. 장부나 전표에서 머리부(header)와 서술부(detail)는 별도의 엔티티에 저장한다**
- 판매(머리부: 판매일자, 판매부서, 판매번호, 부서명, 판매사원번호, 사원명, 고객번호, 고객명, 고객주소)
- 판매내역(서술부: 판매일자(FK), 판매부서(FK), 판매번호(FK), 일련번호, 제품번호, 제품명, 단가, 수량, 금액)
- 서술부에 해당하는 엔티티의 주식별자는 부모 엔티티(머리부)와 연결하여 하나하나를 구분

**원칙2. 코드-코드값의 관계에 있는 속성들은 별도의 엔티티로 구성한다**
- 엔티티에 포함된 종속관계가 이에 해당
- 판매 엔티티에서 부서명을 떼어내어 부서(부서번호, 부서명) 엔티티로 구성
- 판매 → 사원, 고객, 제품 엔티티로 분리

## 8.5 정규화 사례 : 도서관 관리

세금계산서 예 (정규화 이전)
- 세금계산서(접수번호, 공급자 등록번호, 공급자 상호, 공급자 성명, 공급자 주소, 공급자 업태, 공급자 종목, 발행일, 공급가액합계, 세액합계, 비고, 공급일자1~3, 품목1~3, 규격1~3, 수량1~3, 단가1~3, 공급가액1~3, 세액1~3, 총합계금액)
- 다른 부분은 정규화할 필요가 없고 **세금계산서 부분만 정규화**한다

1차 정규화 이후
- 세금계산서(접수번호, 공급자 등록번호, 공급자 상호, 공급자 성명, 공급자 주소, 공급자 업태, 공급자 종목, 발행일, 공급가액합계, 세액합계, 총합계금액)
- 세금계산서내역(계산서 접수번호(FK), 일련번호, 공급일자, 품목, 규격, 수량, 단가, 공급가액, 세액)

3차 정규화 이후
- 세금계산서(접수번호, 공급자 등록번호(FK), 발행일, 공급가액합계, 세액합계, 총합계금액)
- 세금계산서내역(계산서 접수번호(FK), 일련번호, 공급일자, 품목, 규격, 수량, 단가, 공급가액, 세액)
- **업체**(등록번호, 상호, 성명, 주소, 업태, 종목)

정규화 이후 도서관 업무 ERD 구성
- 세금계산서 / 업체 / 세금계산서내역
- 회원(회원번호, 회원이름, 전화번호, 집주소, 이메일, 탈퇴여부, 우수회원 여부, 미반납여부, 가입일자)
- 대출(대출번호, 회원번호(FK), 도서관리번호(FK), 대출일, 반납예정일, 반납여부, 반납구분, 연체료납부여부)
- 도서(도서관리번호, 분류기호, 제목, 저자, 출판사, 출판연도, 구입일자, 국내/해외구분, 신간도서여부, 기타정보, 세금계산서번호(FK))
- 월말결산(년월)
- 독서클럽(클럽ID, 클럽명, 대표자(FK), 인원수, 연령대)

## M:M 관계 해소

- 실세계의 업무 중 대부분은 **M:M 관계**
- 키엔터티와 키엔터티 간에는 대부분 M:M 관계
- 지속적으로 발생되는 대다수의 ENTITY는 M:M 관계
- M:M 릴레이션쉽은 **새로운 릴레이션 엔터티를 추가하여 M:1 관계로 변경**한다
- 예) 제품 : 공급자(M:M) → 제품공급 릴레이션 엔터티(현재가, 수량, 단위)를 추가

### 속성 없는 관계 엔터티 (Intersection Entity)

- ATTRIBUTE가 없는 Intersection Entity는 양쪽의 상호 참조사항만 가진다
- Intersection Entity는 "Entity는 반드시 Attribute를 가져야 한다"는 원칙을 지키지 않을 수 있다
- 이런 Entity는 항상 **UID bar에 의해 UID가 지정**된다
- 예) 출연내역(출연료, 배역) — 영화 : 배우(M:M)
- 단, 최대한 속성을 채워서 엔터티의 체면을 지켜라
- 선택적 속성이 있다고 해서 손해 볼 것 없다
